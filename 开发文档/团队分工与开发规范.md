## 一、角色分工

### 1.2 各角色职责

#### 1.2.1 协调 / 产品（组长）

**职责**
- 定义精灵属性、稀有度、刷新规则与触发规则；将设计文档第八章的待定项逐条确定并形成规则表。
- 维护需求文档与 API 规范，保证 API 规范为接口的唯一真实来源。
- 维护 GitHub Backlog 与 Kanban，跟踪进度，识别阻塞项。
- 组织小组会议，留存会议记录（组内互评的依据之一）。
- 对外汇报与答辩主讲，设计演示脚本。

**交付物**：需求说明书、项目开发计划、规则表、API 规范、会议记录、答辩材料。

**工具**：GitHub Projects（Kanban / Backlog）、GitHub Issues、Markdown、PowerPoint 或 WPS。

**约束**：范围控制优先于功能扩充。任何新增功能默认进入 Backlog 的 V2 优先级，不在当期迭代内实现。

#### 1.2.2 UI/UX 与美术

**职责**
- 产出核心界面设计稿：地图主界面、精灵抓捕界面、图鉴、我的精灵。
- 产出界面元素的**标注图**与开发用**切图**（界面背景、按钮、应用图标等）。
- 产出精灵立绘（含地图图标）与设计规范（主色、字号、圆角、间距）。

**交付物**：设计稿、标注图、切图资源包、设计规范、精灵立绘 8~12 张。

**工具**：墨刀 / 即时设计 / Figma、AI 生图工具 + Photoshop / 稿定、iconfont。

**约束**
- 精灵立绘须为原创形象（校园吉祥物），不得使用宝可梦等第三方 IP，以规避版权风险。
- 立绘数量控制在 8~12 张，按地标或院系一一对应；超出该数量将无法在工期内完成。
- 生成立绘须使用统一的 prompt 模板，保证风格一致。
- 地图页与抓捕页优先出高保真稿，其余界面可先出低保真稿。

#### 1.2.3 客户端 · 地图与定位

**职责**
- 接入高德地图 SDK，实现全屏 2D 地图、玩家位置居中、感知半径渲染、精灵在地图上的渲染。
- 实现实时定位采集，并将定位来源抽象为 `LocationProvider` 接口，提供两种实现：线上真实 GPS、调试用 GPX 轨迹回放。
- 实现任务模式：由用户主动开启跑步 / 自习模式后启动前台服务与常驻通知。
- 实现演示模式：支持一键注入预设轨迹或手动触发事件。

**交付物**：地图主界面、`LocationProvider` 抽象及两种实现、任务模式、演示模式。

**工具**：Flutter 3.x、VS Code（Flutter / Dart 插件）或 Android Studio、高德地图 Flutter 插件、Android 真机。

**约束**
- 验收与演示统一使用 Android 真机，不使用 iOS，避免后台定位策略带来的不可控风险。
- `LocationProvider` 接口须在第二阶段开发启动前定型，其后不得变更，以免影响测试与演示模式。
- 时间相关逻辑不得直接调用 `DateTime.now()`，须经统一的 `Clock` 接口，以支持时间加速测试与演示。

**依赖**：UI 提供地图页设计稿；服务端提供「附近精灵」接口。

#### 1.2.4 客户端 · 业务页面

**职责**
- 实现精灵抓捕界面（题目、选项、答题反馈与动效）。
- 实现图鉴、我的精灵、精灵详情、个人中心。
- 封装统一网络层：请求、错误处理、加载状态。

**交付物**：上述页面及其交互逻辑、网络层封装。

**工具**：Flutter 3.x、`dio`、状态管理库（`provider` 或 `riverpod`，全组统一选用其一）。

**约束**
- 在服务端接口完成前，须基于 mock 数据完成页面开发，不得以接口未就绪为由暂停。
- 状态管理库须与角色 3 保持一致，避免混用。
- 动效以实现功能为目标，不做过度设计。

**依赖**：UI 提供全部设计稿与切图；服务端提供业务接口。

#### 1.2.5 服务端 · 基建与数据

**职责**
- 搭建 Spring Boot 工程骨架：统一响应体、全局异常处理、跨域配置。
- 设计数据库表结构（用户、精灵字典、题库、图鉴、背包、轨迹历史）并输出建表脚本。
- 接入 Redis Geo，实现「玩家附近精灵」的查询。
- 提供 `docker-compose.yml`，统一本地开发与云服务器部署环境。
- 负责课程云服务器的环境部署并输出部署文档。

**交付物**：工程骨架、表结构与建表 SQL、`docker-compose.yml`、部署文档。

**工具**：Spring Boot 3.x、JDK 17、Maven、IntelliJ IDEA、PostgreSQL 16 + PostGIS、Redis 7、DBeaver、Docker。

**约束**
- 工程按功能分包（`user/`、`capture/`、`trigger/` 等），不按层分包，以降低多人并行开发时的文件冲突。
- `docker-compose.yml` 须在第一阶段内就绪，避免组员各自手工安装数据库。
- `Clock` 接口由本角色实现并提供。

#### 1.2.6 服务端 · 业务 API

**职责**
- 用户系统：登录、注册、个人信息。
- 图鉴与背包：收集进度、捕获记录、重复数量查询。
- 抓捕结算：接收选项、校验答案、返回结果、写入图鉴与背包。
- 题库抽取：按精灵的 `tag_id` 随机抽取启用状态的题目。

**交付物**：上述业务接口及对应单元测试。

**工具**：同 1.2.5。

**约束**
- 答案校验必须在服务端完成，不得向客户端下发正确答案。
- 接口须先在 API 规范中定义再实现代码。
- 接口须在实现前与角色 4 对齐。

#### 1.2.7 服务端 · 触发算法

**职责**
- 围栏触发：点与多边形的位置判定；进出缓冲带处理（连续两次命中方确认状态切换）。
- 驻留触发：心跳记录、`last_heartbeat_time` 容错、断连清零。
- 轨迹匹配：坐标去噪（速度合理性过滤）、轨迹切割、状态机闭环判定。
- 将全部判定逻辑实现为纯函数，输入坐标与时间戳序列，输出判定结果。

**交付物**：三类判定算法及单元测试。

**工具**：JUnit 5、Mockito。

**约束**
- 实现优先级为围栏 > 驻留 > 轨迹匹配；轨迹匹配为可裁剪项，视第三阶段进度决定取舍。
- 全部判定逻辑须可通过构造轨迹数组完成测试，不依赖真机与实地测试。
- 时间比较须经 `Clock` 接口，不得直接使用系统时间。

#### 1.2.8 测试与质量

**职责**
- 编写测试用例，覆盖各类触发条件、问答结算与边界情况。
- 维护缺陷列表，跟踪修复状态。
- 使用虚拟定位验证真机在各坐标下的表现。
- 产出测试分析报告，并说明 AI 生成的测试用例如何验证其完备性。

**交付物**：测试用例、缺陷列表、测试分析报告。

**工具**：Android 开发者选项的模拟位置功能、虚拟定位应用、服务端轨迹回放接口、`flutter_test`、JUnit。

**约束**
- 轨迹回放工具由角色 3 与角色 7 提供接口，本角色不负责开发该工具。
- 自动化测试覆盖以关键路径为限，不要求全量覆盖。
- 优先验证：围栏进出是否存在状态抖动；答错后的冷却与逃跑逻辑；断网及定位权限被拒时是否降级而非卡死。

## 三、协作流程

### 3.1 任务管理（GitHub Backlog + Kanban）

课程要求展示 Backlog 与 Kanban 的运作情况，**统一使用 GitHub 自带功能，不另建第三方表格**。

**Backlog**：以 GitHub Issues 承载，每个需求/任务一个 Issue，须包含：

| 字段 | 说明 |
|---|---|
| 标题 | 简洁描述任务 |
| 描述 | 验收标准 |
| Labels | `feature` / `bug` / `docs` / `test` 等 |
| Milestone | 对应五个阶段之一（一阶段 / 二阶段 / …） |
| Assignee | 唯一负责人 |
| Story Points | 粗略估算（1 / 2 / 3 / 5 / 8） |
| Priority | `P0`（必须）/ `P1`（重要）/ `P2`（可裁剪） |

**Kanban**：以 GitHub Projects 承载，列固定为：

```
Backlog → To Do → In Progress → Review → Done
```

**规则**
- 每个 Issue 必须有唯一 Assignee，不允许无人认领。
- 每周例会前更新一次看板状态。
- 进度落后时，优先砍 `P2` 的 Issue，而不是延长工期。

### 3.2 版本控制规范

**分支模型（GitHub Flow 简化版）**

| 分支 | 用途 | 规则 |
|---|---|---|
| `main` | 稳定版本 | 禁止直接提交；阶段验收时由 `dev` 合并 |
| `dev` | 集成分支 | 各功能分支合并至此 |
| `feature/<名称>` | 功能开发 | 命名如 `feature/map-page`、`feature/capture-api` |
| `fix/<名称>` | 缺陷修复 | 命名如 `fix/geofence-flapping` |

**工作流程**

```bash
# 1. 同步最新 dev
git checkout dev
git pull

# 2. 创建功能分支
git checkout -b feature/map-page

# 3. 提交（每日至少一次）
git add .
git commit -m "feat(map): 接入高德地图并显示玩家位置"

# 4. 推送
git push -u origin feature/map-page

# 5. 在 GitHub 发起 Pull Request，合并至 dev
```

**提交信息格式**（Conventional Commits 简化版）

| 前缀 | 含义 | 示例 |
|---|---|---|
| `feat` | 新增功能 | `feat(capture): 添加抓捕结算接口` |
| `fix` | 修复缺陷 | `fix(map): 修复定位点不刷新的问题` |
| `docs` | 文档 | `docs: 补充 API 规范` |
| `refactor` | 重构 | `refactor(trigger): 抽取围栏判定为纯函数` |
| `test` | 测试 | `test(trigger): 补充闭环轨迹用例` |
| `chore` | 构建与配置 | `chore: 添加 docker-compose.yml` |

**强制规则**

1. 每日工作前先执行 `git pull`。
2. `build/`、`.idea/`、`*.iml`、本地配置文件不得提交，须在第一阶段完成 `.gitignore`。
3. 接口须先行定义，各角色修改各自的模块目录，避免多人修改同一文件。
4. 禁止使用 `git push -f`。发生冲突须由相关责任人共同处理。
5. 每位成员的 commit 计入 GitHub Contribution，是组内互评的客观依据，须使用本人账号提交。

### 3.3 会议机制

| 频率 | 形式 | 时长 | 内容 |
|---|---|---|---|
| 每日 | 群内文字汇报 | — | 昨日完成事项 / 今日计划 / 阻塞项 |
| 每周 | 例会 | 60 min | 各角色进度汇报与下周计划，会后更新 Kanban |
| 每周 | 技术同步会 | 30 min | 前后端对齐接口变更 |

**会议记录**：每次小组会议留存简要记录（时间、参与人、议题、结论、待办），存于仓库 `docs/meetings/`。课程组内互评明确将「小组会议」列为评分依据。

### 3.4 代码评审

- 每个 Pull Request 合并前须由第二人审阅。
- 审阅要点：是否提交了无关文件；是否存在硬编码的密钥或密码（须置于配置文件并加入 `.gitignore`）；能否编译通过。
- 不要求逐行评审，但不得由提交者自行合并。

## 四、开发规范

### 4.1 接口规范

**统一响应体**，所有接口均返回此结构：

```json
{
  "code": 0,
  "message": "ok",
  "data": {}
}
```

- `code` 为 0 表示成功，非 0 表示失败；错误码表由服务端维护。
- 客户端仅依据 `code` 判断结果，不解析 HTTP 状态码。

**接口定义流程**
1. 服务端在 API 规范中定义接口（路径、参数、示例响应）。
2. 客户端依据规范使用 mock 数据开发。
3. 服务端实现完成后，客户端切换至真实地址联调。

### 4.2 服务端目录结构

```
pkmon-server/
├── docker-compose.yml
├── src/main/java/com/pkmon/
│   ├── common/          # 统一响应体、全局异常、工具类
│   ├── config/          # 跨域、Redis、安全配置
│   ├── user/            # 用户模块
│   ├── capture/         # 抓捕与结算
│   ├── dex/             # 图鉴与背包
│   └── trigger/         # 触发判定（纯函数）
└── src/main/resources/
    ├── application.yml
    └── db/migration/    # 建表 SQL
```

各模块内部自行划分 `controller / service / repository / entity / dto`。按功能分包的目的在于使各角色独占模块目录，减少并行开发冲突。

### 4.3 客户端目录结构

```
lib/
├── main.dart
├── core/            # 网络封装、常量、主题、Clock 接口
├── data/
│   ├── model/       # 数据模型
│   ├── api/         # 接口调用
│   └── mock/        # 模拟数据
├── features/
│   ├── map/         # 地图页与 LocationProvider
│   ├── capture/     # 抓捕页
│   ├── dex/         # 图鉴
│   ├── bag/         # 我的精灵
│   └── profile/     # 个人中心
└── widgets/         # 通用组件
```

### 4.4 命名约定

| 类别 | 约定 | 示例 |
|---|---|---|
| 分支 | `feature/` + 英文短横线 | `feature/capture-page` |
| 数据库表与字段 | 小写 + 下划线 | `pokemon_dict`、`captured_at` |
| Java 类 | 大驼峰 | `CaptureService` |
| Dart 文件 | 小写 + 下划线 | `capture_page.dart` |
| API 路径 | 小写复数 | `GET /api/v1/pokemons/nearby` |

### 4.5 AI 辅助开发规范（要点）

课程明确要求「规范科学地使用 AI 辅助开发」，且各阶段的 AI 过程性文档均为提交内容。详细方案见 `05_AI辅助开发计划.md`，此处仅列强制规则：

1. **AI 生成代码须经人工评审后合入**，不得直接粘贴提交。评审者需能解释该段代码的用途。
2. **所有 AI 辅助过程须留存记录**（提示词、产出、修改），存于 `docs/ai-log/` 按阶段归档。
3. **不得将课程的私有资料、他人代码、密钥、个人信息输入 AI 工具**。
4. **AI 生成的测试用例须人工验证其有效性**，不能以「AI 说通过了」作为测试结论。
5. 各阶段报告须指定一名成员讲解本阶段「与 AI 协作遇到的问题或总结的方法」。

## 七、关键路径与风险

| 风险 | 影响 | 应对措施 |
|---|---|---|
| **GitHub 仓库未就绪** | 无法提交、无法展示 contribution | 10/8 报告前必须完成仓库创建与 Collaborators 邀请 |
| **云服务器账号未开通** | 部署环节阻塞 | 尽快向助教确认开通时间，本地先用 Docker 开发 |
| 高德 Key 实名审核周期长 | 客户端全线阻塞 | 第一阶段内提交申请；期间使用模拟坐标开发 |
| 后台定位在真机不可用 | 驻留与轨迹无法实现 | M0 完成验证；失败则降级为手动打卡方案 |
| 题库内容不足 | 核心玩法无法支撑 | 二阶段前完成 30 道种子题，由非技术成员分头收集 |
| 触发算法延期 | 核心创新点缺失 | 纯函数与模拟轨迹单测，不依赖真机；必要时裁剪轨迹匹配 |
| 前后端进度不同步 | 联调期集中暴露问题 | 接口先行，客户端以 mock 数据并行推进 |
| 美术产出不足 | 界面空壳 | 立绘限制为 8~12 张；先用占位图，后续替换 |
| 三阶段工期仅一周却要求 60% 功能 | 检查点不达标 | 二阶段必须完成 M1 垂直切片，为三阶段留出余量 |
| 版本控制误操作导致代码丢失 | 返工 | 第一阶段统一学习分支规范；禁止 `git push -f` |

**演示日预案**：若现场网络或定位不可用，切换至演示模式与本地模拟数据，或改放预录演示视频。
