====================================================================
一、验证目的
====================================================================
设计里有两处假设必须先验证，否则设计写完也落不了地：
  假设1 本模块可以用“注入 Clock + 内存仓储 + 固定题库替身”的方式独立测试业务规则；
  假设2 事务边界与唯一约束可以在当前工程的依赖条件下实现。
下面逐条给出实测依据。

====================================================================
二、依赖现状实测
====================================================================
命令（工作目录 server）：
  mvn -B dependency:tree
实际输出要点：
  org.springframework.boot:spring-boot-starter-web:jar:3.5.7:compile
    +- spring-boot-starter / -json / -tomcat
  org.springframework.boot:spring-boot-starter-test:jar:3.5.7:test
    +- org.junit.jupiter:junit-jupiter:jar:5.12.2:test
    +- org.mockito:mockito-junit-jupiter:jar:5.17.0:test
结论：
  - 不存在 spring-tx、spring-jdbc、JPA、Hibernate、H2，也没有 jakarta.persistence。
  - 因此 @Transactional 注解当前不可用（连编译都不通过），数据源也不存在。
  - JUnit 5.12.2 与 Mockito 5.17.0 可用，足以支撑 Clock.fixed + 替身的纯规则测试。
影响：设计中 5.2 事务边界与 5.3 唯一约束冲突处理无法在本阶段落地，
  必须等公共依赖（主责胡豪）补齐。这条已写入 design.txt 第十一节缺项1。

三、可行性验证
====================================================================
验证项1 JDK 21 编译并运行目标版本 17 的工程
  命令：mvn -B test（工作目录 server）
  预期：BUILD SUCCESS 且测试数不为 0
  实际：Tests run: 8, Failures: 0, Errors: 0, Skipped: 0；BUILD SUCCESS
  说明：本机 JDK 21.0.12.1，工程 java.version=17，编译与运行均正常。
  结论：假设1 的技术前提成立（JVM 与测试框架可用）。

验证项2 固定时钟测试方式可行
  依据：现有 DemoServiceTest 已使用 Clock.fixed(Instant.parse(...), ZoneOffset.UTC)
  构造服务实例并驱动全部用例，8 个用例全绿。
  实际：见上条同一命令的实际结果。
  结论：本模块沿用同一方式，可复现有效期边界（前 1 秒 / 当刻 / 后 1 秒）而不 sleep。
  未执行：本模块自己的 Clock 注入代码尚未编写（10/31 foundation）。

验证项3 图形化交付可行性
  命令：java -jar plantuml.jar -charset UTF-8 -tpng *.puml
  环境：PlantUML 1.2024.8，本机无 Graphviz，使用内置 smetana 布局
  实际：四张分析图与四张设计图全部导出成功，中文字体正常（skinparam defaultFontName
    设为 Microsoft YaHei），逐张目视核对无乱码、无连线穿透压字。
  结论：图源为可编辑文本、导出图为 PNG，满足“源文件可编辑 + 导出图可普通阅读器打开”。

验证项4 事务与唯一约束
  结果：未执行，无法执行。
  原因：工程无 spring-tx / spring-jdbc / JPA / 数据库驱动。
  因此以下内容在设计里只有方案，没有实测证据：
    - @Transactional 覆盖“幂等记录 + 收录记录 + 挑战状态”的事务边界；
    - capture_record(user_id, spawn_id) 与 answer_attempt(user_id, request_id) 的唯一约束；
    - 并发提交时唯一约束冲突后的回查路径；
    - 重启后查询。
  结论：这些一律标“未执行”，不用内存实现冒充。

====================================================================
四、本阶段结论
====================================================================
可以推进：签名、DTO、JSON 样例、业务规则与边界测试设计、以及用替身实现的单元测试。
不能推进：真实事务、真实唯一约束、真实持久化查询、真实用户隔离。
阻塞点只有一个根因：公共依赖（事务 + 持久化）与认证入口未就位，
  责任人分别是胡豪与闫昕，已登记在 questions.csv 的 Q01、Q02、Q08。
下一步（10/31 foundation）：在 capture 包内落地可编译骨架与接口签名，
  被依赖未到位阻断的路径返回明确错误，不做假实现、不发虚假奖励。
